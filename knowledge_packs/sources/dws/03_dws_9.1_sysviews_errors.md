# 华为云 GaussDB(DWS) 9.1 高频系统视图与典型报错排障手册

> 适用版本：Huawei Cloud GaussDB(DWS) 9.1 / 8.3 | 方言标识：`DWS`

## 1. 常用只读诊断系统视图速查

以下只读 SQL 可在 Data.O.G 在线模式下直接安全调用，辅助定位会话、锁阻塞、表空间与统计信息问题：

### 1.1 排查活跃慢查询与锁阻塞链

```sql
-- 查看当前耗时最长的前 20 条活跃查询
SELECT
    pid,
    query_id,
    usename,
    application_name,
    state,
    enqueue,
    NOW() - query_start AS elapsed,
    LEFT(query, 200) AS query_snippet
FROM pgxc_stat_activity
WHERE state <> 'idle'
ORDER BY elapsed DESC
LIMIT 20;

-- 检查未被授予（waiting）的锁及被阻塞对象
SELECT
    l.pid,
    l.locktype,
    l.mode,
    l.granted,
    c.relname AS target_table,
    a.usename,
    NOW() - a.query_start AS wait_duration,
    LEFT(a.query, 150) AS blocked_sql
FROM pg_locks l
LEFT JOIN pg_class c ON l.relation = c.oid
LEFT JOIN pgxc_stat_activity a ON l.pid = a.pid
WHERE NOT l.granted
ORDER BY wait_duration DESC;
```

### 1.2 表体积、死元组与统计信息新鲜度排查

```sql
-- 排查指定 Schema 下的大表与死元组堆积情况
SELECT
    schemaname,
    relname,
    pg_size_pretty(pg_total_relation_size(relid)) AS total_size,
    n_live_tup,
    n_dead_tup,
    last_vacuum,
    last_analyze
FROM pg_stat_user_tables
WHERE schemaname NOT IN ('pg_catalog', 'information_schema', 'cstore')
ORDER BY pg_total_relation_size(relid) DESC
LIMIT 30;
```

## 2. DWS 典型报错原因与精准修复方案

### 错误 1：主键或唯一约束缺失分布键 / 分区键
- **典型报错**：`PRIMARY KEY / UNIQUE constraints must contain all distribution columns` 或 `UNIQUE constraint must include all partitioning columns`
- **根因**：分布式 Hash 表和分区表要求所有本地唯一约束索引能由分布键/分区键路由到唯一定位节点/分区，否则无法跨节点保证全局唯一性。
- **修复方案**：
  1. 将全部 `DISTRIBUTE BY HASH(...)` 列及 `PARTITION BY (...)` 列加入 `PRIMARY KEY` 或 `UNIQUE` 组合；
  2. 或改用列存普通索引 / `HSTORE_OPT` 合并键策略，在 ETL 加工阶段去重。

### 错误 2：HStore Opt 与 Delta 参数冲突
- **典型报错**：开启 `ENABLE_BINLOG = ON` 或创建 `HSTORE_OPT` 表时提示参数冲突（`enable_binlog` 与 `enable_delta` 不兼容）
- **根因**：Binlog 增量捕获机制依赖 `HSTORE_OPT` 行版本管理，与传统列存 `ENABLE_DELTA` 机制互斥。
- **修复方案**：建表或 `ALTER TABLE` 时显式移除或关闭 `ENABLE_DELTA = OFF`，仅保留 `ENABLE_HSTORE_OPT = ON, ENABLE_BINLOG = ON`。

### 错误 3：全局队列排队超时或内存不足
- **典型报错**：`ERROR: memory is temporarily unavailable` 或 `wait global queue` 长期卡住
- **根因**：单条 SQL 并发预估内存过大被 CCN 全局资源队列限流，或大表 Broadcast / Skew 引发单 DN 内存飙升。
- **修复方案**：
  1. 先查 `pgxc_thread_wait_status` 确认是 `wait global queue` 还是单机计算 OOM；
  2. 使用 `pg_catalog.table_distribution('schema.table')` 排查是否分布键严重倾斜；
  3. 对过期统计信息表执行 `ANALYZE`，消除优化器误判导致的大表 Broadcast。

### 错误 4：不允许修改已建表的分布键或列类型受限
- **典型报错**：`cannot alter column type of distribution column` / `cannot alter distribution key`
- **根因**：分布列类型或分布键定义改变会导致全量数据所在 DN 物理位置变化，不能原地直接 `ALTER COLUMN TYPE`。
- **修复方案**：采用影子表迁移重建（`CREATE TABLE new_tbl (...) DISTRIBUTE BY ... AS SELECT ...` -> 校验行数与授权 -> 原子重命名切换；若集群启用 `ENABLE_RECYCLEBIN`，清理旧表时按需评估是否使用 `PURGE`）。

### 错误 5：大集群误查 `pgxc_get_table_skewness` 拖慢或超时
- **现象**：查询全库倾斜视图耗时数分钟甚至触发网关超时。
- **根因**：`pgxc_get_table_skewness` 会全量汇总库内所有对象分布信息，表数量达万级时开销极高。
- **修复方案**：改用靶向单表函数 `SELECT * FROM pg_catalog.table_distribution('schema.table');`，按 `pg_stat_user_tables` 筛选 TOP 大表逐个排查。

### 错误 6：只读连接下执行写操作被拦截
- **典型报错**：`cannot execute INSERT/UPDATE/DDL in a read-only transaction`
- **说明**：Data.O.G AI 助手默认使用只读沙箱通道运行探索查询；所有 `CREATE` / `ALTER` / `DROP` / `INSERT` / `UPDATE` / `DELETE` / `VACUUM` 必须作为提案由用户在对话框内**二次确认**后执行。

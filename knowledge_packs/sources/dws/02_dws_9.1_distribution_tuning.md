# 华为云 GaussDB(DWS) 9.1 分布键、存储倾斜与查询调优指南

> 适用版本：Huawei Cloud GaussDB(DWS) 9.1 / 8.3 | 方言标识：`DWS`

## 1. 分布键选型与 Skewness 倾斜黄金准则

MPP 集群的性能取决于各 DN 节点负载均衡，分布键选择不当会引发**存储倾斜**与**计算单点木桶效应**：

- **选键原则**：
  1. 优先选择基数大（Distinct 值多，至少远大于 DN 数量）、无大量 `NULL` 或默认值（如 `-1`、`''`）的列。
  2. 优先匹配核心大表间最高频 `JOIN` 与 `GROUP BY` 关联键，使算子在 DN 本地完成（Collocated Join），消除跨节点重分布（Redistribution）。
  3. 若单一列基数不足，使用多列组合分布键 `DISTRIBUTE BY HASH(col1, col2)`。
- **表倾斜率诊断（DWS 9.1 生产最佳实践）**：
  - **推荐做法**：对单张表优先调用 **`pg_catalog.table_distribution('schema.table')`**，精准输出各 DN 占用的存储字节与倾斜情况，轻量无全库扫描风险。
  - **避坑提醒**：在万级以上表数量的生产大集群中，**避免全库执行 `pgxc_get_table_skewness`**，该视图会批量扫描全库元信息导致 catalog 锁竞争与极高耗时。

```sql
-- 推荐：快速诊断单表在各 DN 节点上的空间分布（只读）
SELECT * FROM pg_catalog.table_distribution('dw.dwd_order_detail')
ORDER BY dnsize DESC;
```

## 2. 等待事件瓶颈分析（`pgxc_thread_wait_status`）

当 SQL 响应变慢时，应优先查询全局线程等待视图 `pgxc_thread_wait_status` 定位根因，而非盲目调整并发参数：

| `wait_status` 关键状态 | 典型瓶颈含义 | 推荐排查动作 |
| :--- | :--- | :--- |
| `acquire lock` | 等待表锁/行锁/元数据锁 | 联合 `pg_locks` 与 `pgxc_stat_activity` 查持锁 `pid` 与长时间未提交事务 |
| `wait io` | 本地盘或 OBS 冷数据读取受阻 | 检查列存 CU 膨胀、是否命中冷分区；DWS 9.1 可评估开启 Disk Cache 与 Async I/O |
| `wait global queue` | 在全局资源队列（CCN）中排队 | 查询资源池并发上限与活跃队列，评估是否因内存估算过大导致排队 |
| `wait data` / 网络等待 | 跨 DN Shuffle / Broadcast 阻塞 | 检查 `EXPLAIN ANALYZE` 中是否存在 `Streaming (type: REDISTRIBUTE / BROADCAST)` 大流量传输 |

```sql
-- 按等待事件聚合并发瓶颈（只读）
SELECT wait_status, COUNT(*) AS thread_cnt
FROM pgxc_stat_activity a
JOIN pgxc_thread_wait_status w ON a.query_id = w.query_id
WHERE a.state = 'active'
GROUP BY wait_status
ORDER BY thread_cnt DESC;
```

## 3. 执行计划精读与算子调优（`EXPLAIN ANALYZE` / `PERFORMANCE`）

排查慢 SQL 推荐使用 `EXPLAIN ANALYZE` 或 `EXPLAIN PERFORMANCE`（只读查看执行阶段耗时、行数估算偏差与下盘情况）：

1. **Streaming 算子检查**：
   - 出现 `Streaming(type: BROADCAST)` 且广播对象实际行数巨大，通常是统计信息过期或分布键关联列类型不一致（如 `INT` 关联 `BIGINT`/`VARCHAR`）所致，需执行 `ANALYZE table_name;` 并统一关联列类型。
2. **估算行数 vs 实际行数偏差（E-Rows vs A-Rows）**：
   - 若相差超过 10 倍，立即检查 `pg_stat_user_tables` 的 `last_analyze`，对表或复合条件列采集统计信息。
3. **算子下盘（Disk Spill）与 `work_mem`**：
   - 若 `HashAgg`、`HashJoin`、`Sort` 出现 `Temp File` 写入磁盘且耗时陡增，可在会话级适当提高 `work_mem`（需权衡集群总体内存避免 OOM）或减少无效 `SELECT *` 列裁剪宽度。

## 4. 高效 SQL 改写模式（`NOT IN` / 子查询 / 分区裁剪）

- **`NOT IN` 改写优化**：
  - `WHERE col NOT IN (SELECT k FROM sub)` 一旦子查询返回任意 `NULL` 值会导致整条结果为空，且分布式优化器常难以高效下推；推荐改写为 `NOT EXISTS`（配合 `IS NOT NULL` 语义明确）或 `LEFT JOIN ... WHERE b.k IS NULL`。
- **避免分区键包裹函数导致分区裁剪失效**：
  - 错误：`WHERE TO_CHAR(order_date, 'YYYY-MM') = '2026-03'`（无法触发分区剪枝，全分区扫描）。
  - 正确：`WHERE order_date >= DATE '2026-03-01' AND order_date < DATE '2026-04-01'`。
- **小表过滤前置与减少 `DISTINCT` 滥用**：
  - 优先在关联前于子查询/CTE 中通过 `WHERE` 过滤缩小参与 Shuffle 的数据集；若仅判断存在性请用 `EXISTS` 替代 `COUNT(*) > 0`。

## 5. 列存 CU 膨胀与 `HSTORE_OPT` 写入规范

- **批量入库原则**：列存表每次独立 `INSERT VALUES` 都会生成小 CU（Compression Unit）并产生大量 Delta 小文件，严重拖慢扫描速度并推高 `wait io`。推荐使用 `COPY`、外表（GDS/OBS）或大批量 `INSERT INTO ... SELECT`。
- **高频更新场景切换**：若业务确实存在高并发单条 Upsert/Delete，应选用 `ENABLE_HSTORE_OPT = ON`，避免普通列存产生严重死元组堆积。
- **定期治理**：定期关注 `n_dead_tup`，对膨胀严重的非 HStore 表在业务低峰执行 `VACUUM` 或 `VACUUM FULL`。
